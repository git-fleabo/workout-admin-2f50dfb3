# Train & Track audit — 11 October 2026

## Assessment

The app has a substantial working foundation, but the primary programme-to-workout path is currently blocked for Base Strength personal programmes. Exports fail in production. Workout correction and offline replay have reproducible failure cases that can lose or duplicate records. These should be resolved before adding features.

This was an audit, with no product fixes, programme edits, session saves, deletions, deployment, or database migrations. The user completed sign-in. Signed-in observations below refer to [the published app](https://workout-admin.lovable.app/) showing **Build 20261011T1419**. Code references refer to repository revision **7d6f07e**; the visible build number does not prove that revision is the deployed source.

**Evidence levels:** Live = observed in the signed-in published app or current database; reproduced = real client functions exercised locally with mocked requests; code = implementation inspection, with no live failure induced. P1 means a core workflow is blocked or records are at risk; P2 means incorrect output or meaningful reliability/accessibility gaps; P3 means usability or longer-term hardening.

### A1 — Next strength session is unreachable

Plan shows an active Volume/Intensity personal programme with 54 saved sessions and a next workout. Today shows mobility, daily practice, supporting plans, recent workouts, and the kettlebell picker, but no strength-programme offer. Following “Go to next workout” returns to this dead end. The planned start date is 12 October; the implementation does not filter these offers by date, so the future date does not explain the omission.

In `src/lib/supabase-programmes.browser.ts:825`, `getCurrentProgrammeWorkoutOffersClient` requires a generic method implementation before reaching its personal-session branch. `src/lib/programme-methods.ts` has no generic implementation for the three Base Strength methods. Local fixtures for Volume/Intensity, Bullmastiff, and DUP each returned an empty offer list despite an active personal programme and an unstarted session. Starting a current programme workout also resolves through this empty offer list.

**Repair:** Resolve the saved personal session before requiring a generic method generator. Preserve the saved prescription and any reviewed overlay. Add positive tests for all three Base Strength methods, then verify Plan → Today → start → log → completion with an explicitly authorized disposable lifecycle and exact cleanup.

### A2 — JSON and CSV downloads fail

Settings → Your data → either download button produces a Supabase error: `column entry_metrics.session_entries does not exist`, code `42703`. The browser records failed REST requests. Both formats call the same export loader.

`src/lib/supabase-export.browser.ts:15` selects `*`, while dependent queries use keys such as `session_entries!inner.sessions!inner.person_id` without embedding those relations in the select. Similar malformed filters occur for sets, metrics, blocks, and suggested-workout children. [PostgREST's embedding documentation](https://docs.postgrest.org/en/stable/references/api/resource_embedding.html) describes the required relation selection and filtering structure.

**Repair:** Fetch child rows through explicit embedded relations or scoped parent IDs, paginate, and keep scope tied to the selected training profile. Verify both actual downloads and their contents, including an empty profile and a profile with setless activities.

### A3 — Correction can delete both original and replacement

`replaceWorkoutSessionClient` in `src/lib/supabase-log.browser.ts:967` saves a replacement, deletes the original, then relinks plans. If deleting the original commits but its response is lost, the catch block deletes the replacement and rethrows. A local mock simulated this exact response-loss sequence: two delete calls occurred and neither session survived.

This is a demonstrated client failure mode, not evidence that existing records have already been lost. The live correction/delete path was not exercised.

**Repair:** Move correction and plan relinking into a single transactional server operation, preferably preserving the original session identity. Give retries a stable operation identifier and a way to resolve an uncertain result. A transport error must not trigger deletion of a successfully saved replacement based on an assumption that the original still exists.

### A4 — Offline saves do not reach the queue

`addWorkoutSessionClient` defaults to `{}` and only enqueues when `options.queueWhenOffline` is true (`src/lib/supabase-log.browser.ts:669,956`). Normal logger callers omit that flag; no production call sets it true. The explicit false caller is correction. Additionally, profile, activity-type, and exercise reads happen before the queue catch block, so losing connectivity during those reads cannot enqueue even if the flag is enabled.

**Repair:** Define a complete offline contract: retain a local draft, prepare saves from cached/validated references, enqueue a stable operation, display pending status, and reconcile after connection returns. Verify offline before saving, connection loss during saving, and reload while offline. Simply enabling the flag is insufficient because of A5 and A10.

### A5 — Queue replay can duplicate records and leave plans pending

`src/lib/workout-offline-queue.ts:93` has no in-flight lock. Two overlapping flush calls read the same queue and issue two save RPCs for one item; this was reproduced locally. The database save operation generates a fresh session identity and has no client idempotency argument, so a retry after a committed save with a lost response also risks duplication.

The queue retains save payloads but not the loaded suggested-workout identity or completion operation. Replay saves the session without the separate planned-session completion step. That can leave a saved workout disconnected from its plan and strength progression. This part is code evidence; a live queued programme workout was not created.

**Repair:** Serialize queue processing, add server idempotency, retain plan provenance, and reconcile saving plus plan completion atomically or through a durable state machine. Test concurrent online events, two tabs, interrupted retries, and a planned session whose save response is lost.

### A6 — Weekly Review confuses support completion with strength progress

The current weekly review reports one completed programme session and explains that each completion moves the programme forward. That completed plan is shoulder mobility support, with `program_workout_id` null. The active strength assignment remains at position zero; its progression is correctly unchanged.

`src/lib/supabase-weekly-review.browser.ts:634` counts any completed suggestion with an assignment ID, without requiring a programme workout ID. Supporting plans intentionally carry an assignment link.

**Repair:** Count strength advancement only for plans with both links, and report supporting completions separately. Verify that review totals agree with the progression rules rather than changing those rules.

### A7 — Base Strength review guidance describes nonexistent work

The coach card says “No unstarted strength sessions to review” and suggests resuming or finishing a current session, despite the active programme's unstarted saved sessions. `src/lib/personal-strength-review.ts:155` intentionally excludes Base Strength plans, while `src/components/programme-refresh-card.tsx:235` treats that unsupported review path as an empty programme.

**Repair:** Explain which review workflow the programme supports, including its source-specific progression and explicit plus-set review where applicable. Link to the saved programme editor. Distinguish unsupported review, no eligible sessions, and an already-started session.

### A8 — Climbing grade chart has no usable numeric series

Progress displays month labels and a grid for climbing grade progress, but no bars. `src/lib/climbing-metrics.ts:65` returns string grades such as climbing grade labels; `src/routes/progress.tsx:947` passes `highestGrade` to a numeric bar chart. The reducer also uses locale string comparison and can compare different grade systems together.

**Repair:** Map grades to validated ordinal values within each grading system, retain the original labels for display, and keep incompatible systems separate. Add an explicit empty/unsupported state rather than a blank plot. Test common grades and mixed systems.

### A9 — Downloaded data would still be an incomplete backup

Even after fixing A2, the export return object (`src/lib/supabase-export.browser.ts:172`) omits personal programmes and their saved sessions, strength-week reviews, coaching preferences/decisions/outcomes, mobility runs/drills/assessments, and location-to-equipment links. These omissions prevent reconstruction of important personal setup. Programme ID gathering also treats owned programme rows as if they have `program_id`, although their primary field is `id`.

**Repair:** Define whether JSON is a complete recoverable profile backup, version its schema, include the required linked records/catalogue references, and test export → reconstruction in an isolated database. State CSV's narrower scope clearly; avoid implying it is equivalent to the profile backup.

### A10 — Refresh and account verification conflate connectivity with access

Three parallel selects using one expired test session issue three refresh requests; there is no shared refresh promise in `src/lib/supabase-public.ts:139`. Supabase refresh tokens rotate, with a limited reuse allowance; serialize refreshes to avoid races and redundant requests. See [Supabase session documentation](https://supabase.com/docs/guides/auth/sessions).

Separately, the auth gate catches every verification error, clears the session, and displays “This account is not approved for this app” (`src/components/supabase-auth-gate.tsx:55`). A connectivity or service failure is therefore treated as an approval failure. This was inspected in code, without forcing a live logout.

**Repair:** Share refresh work across concurrent callers, handle stale responses safely, and distinguish denied access from transient/network errors. Preserve recoverable local work and offer a retry. Test expiry under parallel page loading and offline reload.

### A11 — Shared labels are visually present but not associated

Signed-in logger snapshots show unnamed date, exercise/source/type controls and several climbing numeric controls. The shared `FieldLabel` in `src/components/workout-logger/form-bits.tsx:33` has no association with the corresponding input. Other areas, such as the mobility drill editor and kettlebell selectors, do expose appropriate accessible names.

**Repair:** Give each control a stable ID and associated label or a meaningful accessible name. Cover shared logger forms first, including switches and repeated set rows. Verify keyboard navigation, dialog focus, and screen-reader names. This was a targeted accessibility review, not a formal WCAG certification.

### A12 — Two lockfiles describe different dependency stacks

The manifest requests newer TanStack and Lovable packages than `package-lock.json` and the installed npm tree. `npm ls` reports invalid versions. A disposable copy of the manifests fails `npm ci --dry-run --ignore-scripts --audit=false --fund=false` with `EUSAGE` due to lockfile mismatch. The committed `bun.lock` matches the newer manifest; Bun was unavailable locally.

The installed npm tree reports 23 advisory package findings: 2 critical, 12 high, 7 moderate, and 2 low. This describes the stale npm tree, not a proven vulnerability in the published build. For example, installed seroval is 1.5.2 while `bun.lock` contains 1.6.8; the relevant [seroval advisory](https://github.com/advisories/GHSA-mv8w-475r-vwqw) fixes the reported issue in 1.5.3. Installed shell-quote 1.10.0 is reached through development tooling; see [its advisory](https://github.com/advisories/GHSA-pqg4-j6r4-53mv).

**Repair:** Choose and document the canonical package manager, synchronize/remove the competing lockfile appropriately, run a fresh locked install, and rerun checks and the dependency audit against that exact stack. Then verify the published build independently. Do not blindly upgrade all packages based on the stale report.

### A13 — Review policy ownership predicate binds to the wrong row

The live strength-week-review policies compile the comparison as `assignment.person_id = assignment.person_id`. The unqualified `person_id` in `supabase/migrations/20261005174824_harden_strength_week_review_loop.sql:18,32,41` resolves inside the assignment subquery rather than to the outer review row.

The assignment table's own RLS still limits accessible rows. This is not evidence of arbitrary cross-user access. It weakens the intended review-to-assignment consistency check for an account managing multiple accessible profiles. There are currently no review records or observed mismatches.

**Repair:** Explicitly qualify the outer review owner and add an invariant enforcing that review and assignment belong to the same person. Test with two profiles accessible to one manager as well as an inaccessible profile.

### A14 — Mobile previews bury actions beneath repeated prescription text

At 390 × 844, Today has no horizontal overflow. However, the selected “Recycle!” kettlebell preview expands 30 movement rows, repeats the movement instructions at both movement and set level, and prints the entire repeated AMRAP sequence. The preview is approximately **9,206 pixels tall**; the start button follows it. The expanded page is approximately 11,560 pixels tall. Plan likewise exposes a long saved-session editor rather than a compact route to the next action.

**Repair:** Lead with workout summary, duration, equipment, sequence and start action; put the detailed preserved prescription behind an accessible disclosure. Group repeated sequences without changing the underlying logger targets. Use “1 rep”/“1 movement” and remove duplicate “Week 1” labels. Keep detailed editing available after the next workout is clear.

### A15 — Older records eventually crowd out recent charts

Dashboard sessions, 1RM tests and bodyweight queries are sorted ascending and capped at 1,000 (`src/lib/supabase-dashboard.browser.ts:460`). Once a series exceeds that cap, later records disappear from the result. Other history queries also use fixed caps without a clear paging contract. Current session volume is below this threshold, so no present loss was demonstrated.

**Repair:** Use bounded date windows/server aggregation for charts and explicit pagination for history and export. Test beyond the cap and surface incomplete results rather than silently accepting truncation.

## Recommended repair milestones

1. **Restore a trustworthy core loop:** fix A1 and A2; make correction atomic (A3); reconcile the package-manager stack (A12) so validation is reproducible. Verify actual exports and a disposable programme lifecycle with explicit authorization and exact restoration.
2. **Make saving and recovery dependable:** implement offline behavior, idempotent replay, planned-session reconciliation and session recovery together (A4, A5, A10). Exercise response-loss and concurrency scenarios in an isolated database/browser environment.
3. **Make review and progress truthful:** separate strength/support counting, explain supported coach behavior, repair grade charts, complete the backup contract and harden review ownership (A6–A9, A13).
4. **Reduce friction:** label shared controls, shorten previews while preserving prescriptions, paginate long-lived data, and review security/performance advisories (A11, A14, A15).

Further live write validation needs a separately authorized disposable test workflow. Nothing in this audit changes the saved programme, training history or coaching decisions.
